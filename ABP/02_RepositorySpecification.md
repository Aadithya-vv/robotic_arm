# Purpose

This document defines the engineering repository that shall contain the entire TaskGraph project.

The repository is not merely a storage location for source code.

It is the permanent engineering knowledge base of the project.

Every architectural decision, engineering specification, implementation artifact, report, and source file shall ultimately reside inside this repository.

The repository becomes the authoritative source of truth after Architecture Blueprint approval.

---

# Repository Philosophy

The repository is designed according to four principles.

## 1. Repository First

The repository is the permanent memory of the project.

Engineering knowledge shall never exist only inside conversations.

---

## 2. One Source of Truth

Every engineering artifact exists in exactly one location.

Duplicate specifications are prohibited.

Duplicate prompts are prohibited.

Duplicate documentation is prohibited.

---

## 3. Predictable Organization

Every file has one logical location.

Engineers should immediately know where an artifact belongs without searching.

Repository organization shall remain stable throughout Version 1.

---

## 4. Architecture Before Code

The repository is generated from architecture.

The implementation follows the repository.

Implementation shall never redefine repository organization.

---

# Repository Objectives

The repository shall:

- Organize every engineering artifact.
- Support engine-by-engine development.
- Support repository-first implementation.
- Support long-term maintenance.
- Support future expansion.
- Remain understandable to new contributors.
- Act as permanent project documentation.

---

# Repository Structure

The repository shall contain the following top-level directories.

```text
TaskGraph/

ABP/
GBP/

Specifications/

Prompts/

Implementation/

Reports/

Documentation/

Research/

Assets/

Tests/
```

No additional top-level directories shall be created without architectural approval.

---

# Directory Responsibilities

## ABP

Contains architect-authored blueprint documents.

These define project identity, engineering standards, architecture, repository organization, engine catalogue, and Codex instructions.

ABP documents are manually written.

---

## GBP

Contains architect-expanded documents generated by Codex.

These documents translate architecture into implementation-ready engineering artifacts.

GBP documents are generated once and reviewed before repository generation.

---

## Specifications

Contains implementation-grade engineering specifications.

Every Engine owns exactly one specification.

Specifications become frozen before implementation.

---

## Prompts

Contains Framework Prompts.

Each Engine owns one Framework Prompt.

Prompts instruct Codex how to implement an Engine while respecting the frozen architecture.

---

## Implementation

Contains production source code.

Every Engine owns its own implementation directory.

Implementation follows specifications.

---

## Reports

Contains Implementation Reports generated after each completed Engine.

Reports document:

- work completed,
- files created,
- implementation decisions,
- testing summary,
- known limitations.

Reports provide engineering traceability.

---

## Documentation

Contains user-facing and developer-facing documentation.

Examples include:

- project overview,
- installation guide,
- user manual,
- API documentation.

Documentation is independent of engineering specifications.

---

## Research

Contains research artifacts.

Examples include:

- literature review,
- novelty analysis,
- experiment notes,
- evaluation metrics,
- publication material.

Research documentation remains separate from engineering implementation.

---

## Assets

Contains static project resources.

Examples include:

- diagrams,
- logos,
- presentation material,
- UI mockups,
- illustrations.

---

## Tests

Contains automated and integration tests.

Each Engine owns corresponding test suites.

Testing shall remain independent from production implementation.

# Repository Rules

The repository follows the following immutable rules.

- One Engine owns one implementation directory.
- One Engine owns one specification.
- One Engine owns one framework prompt.
- One Engine owns one implementation report.
- One Engine owns one primary responsibility.
- Every implementation is traceable back to its specification.

---

# Repository Naming Convention

Repository names shall remain descriptive, stable, and human-readable.

Document identifiers shall never change after approval.

Engine names shall remain consistent across:

- architecture,
- specifications,
- prompts,
- implementation,
- reports.

Consistency takes priority over abbreviation.

---

# Repository Integrity

Repository integrity shall be preserved throughout the project.

The repository shall never contain:

- orphaned specifications,
- undocumented implementations,
- duplicate prompts,
- conflicting ownership,
- unreferenced Engines.

Repository consistency is considered an architectural requirement.

---

# Codex Interaction Model

Codex interacts with the repository using a repository-first workflow.

Before implementing any Engine, Codex shall:

1. Read ABP.
2. Read GBP.
3. Read the target Engine specification.
4. Read the Framework Prompt.
5. Read required dependency specifications.
6. Implement only the requested Engine.
7. Generate an Implementation Report.
8. Stop.

Codex shall never modify unrelated Engines.

---

# Repository Evolution

Version 1 repository structure is considered stable.

Future versions may introduce additional directories only through an approved Engineering Decision Record.

Version 1 prioritizes stability over flexibility.
